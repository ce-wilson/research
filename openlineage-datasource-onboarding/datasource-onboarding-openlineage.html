Implementation analysis · OpenLineage 1.52.0 / spec 2-0-2

Datasource Onboarding on OpenLineage

The model already separates the three things this problem requires kept apart: identity (namespace + name), description (facets), and access — which OpenLineage deliberately does not model at all. That split is what makes incremental curation, replica provenance, and credential isolation fall out of the design rather than get bolted onto it.

01What the use case actually asks for

Six requirements, separable, shippable in almost any order. Only the first two are prerequisites for the rest.

IDAs statedAs a modeling problem
RQ-1 “I don't have all of the connections, details, data profiles etc. I need to manually gather and add as I find it.” Incremental, out-of-order, partial metadata accrual against a stable entity identity — with no job run to hang it on.
RQ-2 “at first we download sample reports or database exports, usually saved as a csv sometimes a json file” A file artifact is a first-class dataset standing in for a datasource not yet reachable. Later superseded — never deleted.
RQ-3 “we get data from a replica but it could be a different platform” Two distinct physical datasets on two platforms representing one logical entity. Both independently addressable.
RQ-4 “document the original source of the data and the data's provenance (that it's from a replica)” A directed, traversable edge replica → origin, plus an assertion of how. Must survive lineage queries.
RQ-5 “connection details… stored and maintained separately from what we show the users as the data source” Split identity from access. The published identifier must be derivable without secrets and stable across credential rotation.
RQ-6 “integrated with our in-house ontology tool, so I'll need to classify it by ontology” Attach external taxonomy terms at dataset and column granularity, round-trippable to an external system of record.

One framing correction before anything else

OpenLineage is a wire format, not a database. It has no query API, no curation UI, no edit history, and no partial-update semantics of its own. Your curation tool must own the master record; OpenLineage is the emission and interchange format projected out of it. Do not try to use a lineage backend as the system of record for in-progress curation — it is not built for editing, and the incremental model below depends on you being able to re-derive the full picture locally.

02The model, in the parts that matter here

Three event types, not one

The spec root is oneOf: [RunEvent, DatasetEvent, JobEvent]. Most OpenLineage material is about the first. The second and third — collectively “static lineage” or “design lineage” — are what this use case runs on, and they are structurally forbidden from referencing a run.

EventRequiresStructurally forbiddenUse it for
RunEvent run, job — Something actually executed. Profiling runs, real ingestion, and — as a compatibility fallback — asserted replication.
DatasetEvent dataset job, run The registration primitive. Every curation act. Schema, docs, ownership, tags, classification.
JobEvent job run Declaring a job's inputs and outputs at design time — a replication or extract you know happens but never observe.
Source: spec/OpenLineage.json lines 28–102, 303.

The spec's own documentation names this use case almost verbatim. DatasetEvent exists to “attach metadata to a dataset outside the context of a job or a job run… static schema extraction, documentation generation, or governance,” emitted “when a dataset's metadata is updated or first defined.” Registration does not require inventing a fake job, and does not require the metadata to be complete.

Identity is two strings, and facets are optional

A dataset is the pair (namespace, name). Everything else is commentary. The minimum legal registration event carries no facets at all: 

{
  "eventTime": "2026-08-29T10:00:00Z",
  "producer":  "https://your.org/datasource-registry/1.4.2",
  "schemaURL": "https://openlineage.io/spec/2-0-2/OpenLineage.json#/$defs/DatasetEvent",
  "dataset": {
    "namespace": "oracle://prod-ora.provider.example:1521",
    "name":      "ORCL.SALES.ORDERS"
  }
}

That is the whole answer to RQ-1. Declare identity on day one; add facets as you learn them, one event per fact, carrying only what changed.

Facet mechanics you will rely on

MechanismBehaviourConfidence
BaseFacet extension Requires _producer + _schemaURL, sets additionalProperties: true. Any custom facet key is accepted and stored verbatim, retrievable on query. Verified
_deleted: true Retracts a facet. Valid on dataset and job facets only — “not run or input/output facets, which are valid only for a specific run.” Verified
Event-level: additive “All metadata is additive… we might send additional events specifically for those datasets without re-emitting previously observed inputs or outputs.” Facets you don't mention persist untouched. Verified
Facet-level: replacement “A facet is an atomic piece of metadata identified by its name… emitting a new facet with the same name for the same entity replaces the previous facet instance for that entity entirely.” Not a deep merge. Verified
Static facets persist forward A dataset facet “applies to all versions moving forward until replaced by a new one.” Deletion is destructive, not a rollback: “we don't get back to the previous one.” Verified
facets vs. inputFacets Split by stability: facets is what's static run-to-run; inputFacets/outputFacets are per-read/per-write and exist only on a RunEvent. Verified
Consequence A DatasetEvent cannot carry data profiles. dataQualityMetrics and inputStatistics are input facets, unreachable without a run. Inferred

The producer rule this forces — and the way it will bite you

The two rules compose into one constraint that governs every line of producer code you write. You may add new facets freely without resending the old ones. But changing one field inside an existing facet means re-emitting that entire facet object. There is no partial-update path within a facet.

Concretely: emitting a schema facet containing the one column you just documented destroys every other column. Emitting tags with one new tag drops all the others. The failure is silent and it looks like data loss, not like an error.

So the curation tool must materialize the complete current value of any facet it touches, from its own master record, and send the whole thing. Enforce that in a single serialization layer rather than at each call site. R-01

Snowflake is a one-way door

Two namespace formats exist: snowflake://{org}-{account} and the legacy snowflake://{locator}.{region}.{cloud}. 04Replica provenance — the decision that matters

You need to record that data was read from a replica, and that the replica derives from a named production origin on a different platform. Four mechanisms can express something like this. Only two are right, and the obvious-looking one is actively wrong.

Option A — Symlinks
Rejected

The facet asserts identifiers “refer to the same entity,” producing a unified graph. Collapsing prod and replica into one node destroys the exact fact you must document.

Option B — lineage facet
Target model

Purpose-built for “lineage curated in a data catalog.” Semantically exact. Blocked today: in no release tag, no consumer support.

Option C — replication job
Ship this now

Two datasets plus an explicit job carrying the edge. Works against every backend. Converges with B.

Option D — dataSource
Complement

Two optional strings. Records what the datasource is; creates no traversable edge. Use alongside B or C, never instead.

Why symlinks is the trap

SymlinksDatasetFacet looks like the answer — it exists to relate two identifiers for one thing. But read its definition: it lists “alternative identifiers for a single dataset… allows OpenLineage to understand that these different identifiers refer to the same entity, creating a unified lineage graph.” It is for an S3 path and its Glue table — one entity, two names.

A production Oracle table and its Snowflake replica are two physical copies with different freshness, different access rules, and different platforms. Symlinking them merges the nodes and erases the one fact RQ-4 requires you to keep: that you read the replica, and were not permitted to read production.

The design proposal draws exactly this line

The static-lineage proposal lists as separate motivating use cases: “create dataset symlinks more easily,” scoped explicitly to naming variants — “FQDN versus hostname, including region vs. not, differing query params” — and “dataset connections: ability to connect 2 dataset entities without additional information about the run that created that connection.”

Yours is the second. Symlinks resolve two names for one thing; you have two things.

The compatibility gradient inside Option C

VariantEventConsumer compatibilitySemantic fit
C-1 Synthetic RunEvent pair for a replicate.* job Highest Every backend consumes RunEvent Weakest — asserts a run you never observed, with a fabricated runId. Honest only if timestamps are labelled as assertions.
C-2 JobEvent with declared inputs/outputs Pending Static ingestion is uneven Strong — this is the design-time declaration event. No fabricated run.
C-3 JobEvent + LineageJobFacet.entries Lowest Unreleased Strongest — avoids the Cartesian false edges that matter once one replication job covers many tables.

Why the tiering is safe

B, C-1, C-2 and C-3 all use the same two dataset identities. Shipping C-1 today and adding B later is purely additive — no renaming, no rewriting history, no broken node identity. The compatibility tier is a transport decision you can defer; the model underneath does not change.

05Credentials: the namespace is the vault key

RQ-5 asks for connection details maintained separately from the displayed datasource identity. OpenLineage does not model credentials at all — and its identity grammar is credential-free by construction. That is not an accident you can rely on loosely; it is reinforced in the client.

EvidenceWhat it establishes
No namespace convention across 40+ platforms includes userinfo The published identifier is derivable without secrets
RedactMixin with a _skip_redact class-var allow-list The client's default posture is to redact unless explicitly exempted
DatasourceDatasetFacet exempts name and uri The spec assumes that uri is already credential-free — an assumption you must uphold

Rules

  1. Derive the vault key from the namespace, never the reverse. oracle://prod-ora.provider.example:1521 → datasources/oracle/prod-ora.provider.example/1521. Rotation never changes the namespace, so no lineage node is ever orphaned by a password change.
  2. Never emit userinfo. oracle://user:pass@host:1521 is not a legal namespace, and would fork dataset identity on every rotation.
  3. Sanitize centrally. One sanitize_uri() in the emitter: strip userinfo, drop every query parameter not on an explicit allow-list. Unit-test it.
  4. Never put connection details in documentation.description — free text with no redaction contract.
  5. The user-facing display name — server / database / schema / table — comes from hierarchy + name. That is the credential-free projection RQ-5 asks for.

Where credentials leak — and the reference implementation that already fixes it

JDBC URLs. CatalogDatasetFacet.metadataUri's own spec example is jdbc:mysql://host:3306/iceberg_database, and real JDBC strings routinely append ?user=…&password=…. Because uri is on the redaction exemption list, nothing downstream catches it.

The Java client already solves this. JdbcUrlSanitizer.dropSensitiveData() applies five passes: strip slash-delimited userinfo, strip colon-delimited userinfo, remove user=/username=/password= parameters case-insensitively, collapse duplicated delimiters, then drop the entire query string. Reach it through the public JdbcDatasetUtils, which dispatches over ~15 vendor extractors.

Python has no equivalent — port those five rules. Note the last one is stricter than an allow-list: it discards all query parameters rather than vetting them. Adopt that posture. R-03

One honest qualification

Credential exclusion is convention plus tested implementation, not a normative spec prohibition. No clause forbids putting a password in a namespace — the 28 Naming classes simply give you no parameter with which to do so, and the JDBC path actively strips them. That is strong, but it means the guarantee is yours to maintain in any code path that builds identifiers by hand.

06Ontology: dual-emit, because neither mechanism suffices alone

Schema validationBy the specBy your self-hosted schema

Emit both from one source of truth in the curation tool. The custom facet is the system of record; the tags block is a lossy projection for human search and filtering.

The facet key is not free-form

The spec requires a project prefix: “Custom facets must use a distinct prefix named after the project defining them.” The convention is key {prefix}_{name} in camelCase for a schema class {prefix}{Name}{Entity}Facet in PascalCase — the shipped example being bigQuery_statistics / BigQueryStatisticsJobFacet. A bare "ontology" key is non-conformant and risks colliding with a future standard facet.

_schemaURL is equally constrained: it “must be an immutable pointer… should include a tag of a git sha and not a branch name.” Version it in the path; never point at main. 

"acme_ontology": {
  "_producer": "https://your.org/datasource-registry/1.4.2",
  "_schemaURL": "https://your.org/schemas/openlineage/v2026.3.1/AcmeOntologyDatasetFacet.json",
  "ontologyVersion": "2026.3",
  "classifications": [
    { "termUri": "https://your.org/ontology/term/CustomerOrder", "scope": "DATASET",
      "confidence": 1.0, "curator": "user:jdoe" },
    { "termUri": "https://your.org/ontology/term/TaxIdentifier", "scope": "FIELD",
      "field": "tax_id", "confidence": 0.92, "curator": "service:auto-classifier" }
  ]
},
"tags": { "tags": [        // lossy projection, but it renders
  { "key": "ontology.term", "value": "CustomerOrder", "source": "ONTOLOGY" },
  { "key": "ontology.term", "value": "TaxIdentifier", "source": "ONTOLOGY", "field": "tax_id" }
]}

Host the custom schema at a stable, resolvable URL with the version in the path, so _schemaURL pins a version. spec/registry/ in the OpenLineage repo is for facets contributed upstream — an internal facet does not belong there unless you intend to propose it.

Curation state — do not overload lifecycleStateChange

RQ-1 implies records sit incomplete for long periods, and OpenLineage has no notion of a draft entity. LifecycleStateChangeDatasetFacet looks tempting and is wrong: its enum is closed (ALTER, CREATE, DROP, OVERWRITE, RENAME, TRUNCATE) and describes the data object's lifecycle, not the catalog entry's maturity. Use a tag with a vocabulary you own: 

DECLARED → SAMPLE_ONLY → SOURCE_IDENTIFIED → CONNECTION_ESTABLISHED → CLASSIFIED → PRODUCTION

Once lineage ships it offers a sharper distinction tags cannot express: an omitted inputs means “upstream unknown, still investigating,” while inputs: [] explicitly means “investigated, confirmed no tracked upstream.” That is a genuinely useful curation state.

09Open questions
